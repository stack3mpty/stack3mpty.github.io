给 Axum 补齐 Inner 路由语义：从 #3880 到一个 Stacked PR

2026-09-08

最近我给 Axum 提交了一个小型功能 PR，目标是解决嵌套路由下两个路径 extractor 缺少“当前 Router 视角”的问题：MatchedPath 和 RawPathParams。

对应的是 tokio-rs/axum#3880，最终提交的改动是 PR #3885。

代码量本身不大，但它涉及一个很典型的框架设计问题：

当一个组件被嵌套到更大的系统中时，它应该看到全局上下文，还是只看到属于自己的局部上下文？

Axum 已经在 Path 上开始解决这个问题，这次修改则进一步补齐这套语义。

1. 问题从 Router::nest 开始

假设我们先定义一个可复用的用户路由：

let users = Router::new()
    .route("/users/{user_id}", get(handler));

再把它挂载到租户路由下：

let app = Router::new()
    .nest("/tenants/{tenant_id}", users);

请求 /tenants/acme/users/42 从整个应用看包含两个动态参数：

tenant_id = acme
user_id   = 42

但从 users 子 Router 的视角，它真正定义的只有 /users/{user_id}。理论上，handler 只需要关心 user_id = 42，不应因为外部挂载位置而被迫知道 tenant_id。这就是 reusable router 的封装边界问题。

2. Path 为什么会受到外层 Router 影响

传统行为中，下面的 extractor 会拿到请求路径上的全部 capture：

async fn handler(Path(params): Path<HashMap<String, String>>) {
    // tenant_id 和 user_id
}

这符合 Path 一贯的全局语义，但会让可复用 Router 与最终挂载位置耦合。一个 user_router() 不应该关心自己最终位于 /api、/tenants/{tenant_id}，还是 /organizations/{org_id}/regions/{region}。

3. #3856 引入了 InnerPath

在 #3880 之前，PR #3856 已经新增了 InnerPath<T>：

Path<T>
    = 当前请求中的所有 path captures

InnerPath<T>
    = 当前最内层 Router 自己的 captures
async fn handler(
    Path(all): Path<Vec<(String, String)>>,
    InnerPath(inner): InnerPath<Vec<(String, String)>>,
) {
    // ...
}

对于 /tenants/acme/users/42，两者分别得到：

Path:
[("tenant_id", "acme"), ("user_id", "42")]

InnerPath:
[("user_id", "42")]

4. Axum 如何记录 inner 边界

Axum 内部通过 UrlParams 保存匹配到的 URL 参数。#3856 将它扩展为类似结构：

UrlParams::Params {
    params: Vec<(Arc<str>, PercentDecodedStr)>,
    inner_start: usize,
}

假设参数依次为 tenant_id 和 user_id，且 inner_start = 1，那么 &params[inner_start..] 就是内层 Router 自己的参数。

这套设计没有维护 all_params 和 inner_params 两份数据，而是使用“一份 Vec + 一个索引”，既简单，也避免额外复制。

5. #3880：只有 Path 有 Inner 版本

有了 InnerPath 后，path API 出现了不对称。除了 Path，Axum 还有两个常见 extractor：

MatchedPath
RawPathParams

它们仍然只能看到完整路由视角。

6. MatchedPath 的问题

MatchedPath 返回匹配到的 route pattern，而不是实际 URL。单独的 /users/{user_id} 路由会返回：

/users/{user_id}

嵌套到 /tenants/{tenant_id} 后，它会变为：

/tenants/{tenant_id}/users/{user_id}

子 Router 看到的是完整部署路径，而不是自己定义的 route。对于日志、metrics 和 middleware，这会让同一组件挂载到不同位置后产生不同的 metric label。

7. 增加 InnerMatchedPath

#3880 因此提议加入 InnerMatchedPath：

MatchedPath
    = 完整 matched route

InnerMatchedPath
    = innermost Router 的 matched route
async fn handler(
    matched: MatchedPath,
    inner: InnerMatchedPath,
) {
    assert_eq!(
        matched.as_str(),
        "/tenants/{tenant_id}/users/{user_id}"
    );

    assert_eq!(inner.as_str(), "/users/{user_id}");
}

这与 Path / InnerPath 形成了一组一致的 API。

8. 复用 NestedPath，而不是增加路由状态

一种直接实现是让 Router 同时维护 MatchedPath 和 InnerMatchedPath 两份 extension，但这会增加 routing state。

现有实现已经有 NestedPath，它记录 Router 被 nest 在什么路径上，因此可以直接利用：

完整 MatchedPath
- NestedPath
= InnerMatchedPath
MatchedPath:      /tenants/{tenant_id}/users/{user_id}
NestedPath:       /tenants/{tenant_id}
InnerMatchedPath: /users/{user_id}

核心目标是复用现有 routing context，而不是为了一个 extractor 再增加一套内部 bookkeeping。

9. RawPathParams 的问题更有意思

RawPathParams 是 Path<T> 的低层版本，可以直接遍历参数，避免 Serde 反序列化和部分额外分配：

async fn handler(params: RawPathParams) {
    for (key, value) in &params {
        println!("{key} = {value}");
    }
}

嵌套 Router 中，它仍然返回 tenant_id 与 user_id。既然 #3856 已经记录了 inner_start，问题就变成：是否还需要设计一个 InnerRawPathParams？

10. 为什么没有新增 InnerRawPathParams

如果为 inner variant 复制一份新的 Vec，会违背 RawPathParams 少转换、少分配、直接访问底层参数的定位。因此，更合适的方案是暴露已有边界：

params.inner_start()

调用方可以自己选择 inner slice：

for (key, value) in params.iter().skip(params.inner_start()) {
    // only inner router params
}
额外 Vec 分配：0
额外字符串复制：0
额外参数解析：0

整个方案只多保存一个整数索引。

11. RawPathParams 的结构变化

修改后的结构类似：

pub struct RawPathParams {
    params: Vec<(Arc<str>, PercentDecodedStr)>,
    inner_start: usize,
}

extractor 从内部 UrlParams::Params 同时复制 params 和 inner_start，并公开 pub fn inner_start(&self) -> usize。原来的 params.iter() 完全不受影响，这是一个 additive API change。

12. 全局上下文与局部上下文

如果只看代码，这次修改只是新增一个 struct 和一个 usize getter。更值得关注的是它背后的抽象：

Application
    └─ Router A
        └─ Router B
            └─ Handler

对 Handler 来说，全局与局部两类信息都合理：

全局信息：完整 route、完整 params
局部信息：当前 Router route、当前 Router params

于是 API 逐渐形成：

Path             InnerPath
MatchedPath      InnerMatchedPath
RawPathParams    inner_start

本质上，这是在为 Axum 补全 global routing context 与 local routing context。

13. 为什么 reusable Router 需要它

一个 admin_router() 可能被不同应用挂载在 /admin、/api/v1/admin，或者 /organizations/{org_id}/admin。

如果内部 handler 使用 MatchedPath，route metric 会随 mount location 改变；如果使用 InnerMatchedPath，内部的 /users/{id} 始终保持稳定，Router 的封装边界也就稳定了。

14. 这个 PR 不能直接基于 main

#3880 的设计依赖 #3856，但开始处理时，#3856 仍然是 open PR，main 中还没有 InnerPath 和 UrlParams::inner_start。

如果直接基于 main 实现，就必须重新复制 #3856 的代码，最终 PR 会同时包含两组改动，不仅 diff 巨大，也会与原作者产生重复修改。

15. 使用 Stacked PR

更合理的方法是让自己的 branch 基于 #3856 的 head commit：

main
  │
  │ #3856
  ▼
InnerPath commit
  │
  │ #3880
  ▼
our commit

Git 历史类似：

main
  │
  A
  │
  B
  │
  C   ← #3856 head
  │
  D
  E
  F   ← #3880 changes

当前 PR 真正的增量是 C..F：InnerMatchedPath、RawPathParams::inner_start 和测试，不需要重复实现 InnerPath。

16. 为什么 GitHub 页面看起来仍然很大

upstream PR 的比较目标仍然是当前分支到 tokio-rs/axum:main，而 main 尚未包含 C，因此 GitHub 暂时会显示 A 到 F，也就是 #3856 与 #3880 的总和。

真正属于当前 PR 的 diff 应该这样看：

base = #3856 head
head = our branch

git diff base..head

这也是 PR description 需要明确写出 This PR is stacked on #3856. 的原因。

17. 为什么先开 Draft PR

因为 #3856 尚未 merge，#3880 不能独立进入 main。直接标为 Ready for Review 容易让 maintainer 误以为它已经可以正常合并。

更合理的是先开 Draft PR。等 #3856 merge 后，main 自然包含 C，GitHub 只会显示 D、E、F，再把当前 PR 转成 Ready for Review，协作关系会清晰很多。

18. 这次修改带来的几个体会

不要只根据 issue description 写代码

#3880 看起来只是“add InnerMatchedPath、expose inner_start”，但实现前需要先确认 InnerPath 是否已进入 main、inner_start 在哪里维护、MatchedPath 如何组合 nested route，以及是否已有可复用的 extension。

如果没有先看 #3856，就很容易再造一套重复状态。

先理解数据流，再加 API

matchit
   ↓
route match
   ↓
UrlParams
   ↓
request Extensions
   ↓
Path / InnerPath / RawPathParams

以及：

route pattern
   ↓
MatchedPath
   ↓
nested route composition

理解这些数据流后，方案就很自然：inner params 已经有 inner_start，inner matched path 已经有 nested routing information。

真正好的 patch 往往不是“再造一个机制”，而是把已有信息以正确的 API 暴露出来。

小 PR 也包含 API 设计

对于 RawPathParams，InnerRawPathParams 在表面上更对称，但 inner_start() 更符合其避免额外 deserialize 和 allocation 的性能定位。

API 设计不一定追求表面完全对称，更重要的是保持类型自身的语义。

19. 总结

这个 issue 可以用一句话概括：

Axum 已经为 Path 提供了 inner-router 语义，但 MatchedPath 和 RawPathParams 仍然只能看到整个路由树的信息，因此 #3880 补齐了这部分能力。

MatchedPath
    ↓
新增 InnerMatchedPath

RawPathParams
    ↓
公开 inner_start

设计目标是让完整上下文和局部 Router 上下文同时可用，并且不引入不必要的数据复制。

从更抽象的角度看，它解决的是 reusable component 的封装问题：一个子 Router 不应该因为被挂载到不同路径，就被迫改变自己对 route metadata 的理解。

虽然这是一个相对小的 Axum contribution，但其中涉及的 Router composition、extension state、零额外分配设计和 stacked PR 工作流，都是很典型的开源框架开发问题。

参考：Issue #3880、PR #3885、PR #3856。
