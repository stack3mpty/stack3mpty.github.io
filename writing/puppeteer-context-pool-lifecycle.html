从资源泄漏到生命周期托管：一次 Puppeteer 浏览器资源池改造

2026-09-08

在基于 Puppeteer 的页面渲染服务中，真正难处理的往往不是“如何打开页面”，而是“页面执行结束后，浏览器资源是否仍然处于可靠状态”。

一次看似普通的超时，可能让已经返回失败的任务继续操作浏览器；一个遗漏的归还操作，也可能在几次请求后耗尽整个资源池。

本文分享一次 Browser Context 资源池的生命周期改造，以及如何在修复资源问题的同时保持原有业务语义。

项目背景

该服务基于 Node.js、Koa 和 Puppeteer，主要提供两类能力：

  • 将页面渲染并序列化为 HTML。
  • 将页面渲染后生成截图。

为了避免每个请求都启动一个 Chrome 实例，服务预先创建固定数量的 Incognito Browser Context。请求到来时从资源池借用 Context，创建 Page 执行任务，完成后再归还。

理想的生命周期应该是：

获取 Context
    ↓
创建 Page
    ↓
执行渲染或截图
    ↓
关闭 Page
    ↓
归还 Context

但在异常、超时和浏览器断线等场景下，这条链路很容易被打断。

问题一：Context 被取出后没有归还

原来的 HTML 渲染路径只从资源池获取 Page，没有保留对应的 Context，也就无法在任务结束后归还。

当资源池容量固定时，这个问题非常直接：每执行一次渲染，就永久减少一个可用 Context。资源池耗尽后，后续请求只能一直等待。

除此之外，部分提前返回和异常路径也没有关闭 Page，例如：

  • 页面没有获得有效响应。
  • 页面脚本执行失败。
  • HTML 序列化失败。
  • Puppeteer API 抛出异常。

这些泄漏最终会表现为 Chrome 内存持续增长、请求积压，甚至整个渲染服务失去响应。

问题二：Promise 超时不会停止底层任务

截图路径原本使用 Promise.race 实现 40 秒超时。但这种方式只能让外层 Promise 提前失败，不能真正取消正在执行的 Puppeteer 操作：

截图任务仍在运行
        ↓
外层 Promise 超时返回
        ↓
Context 被放回资源池
        ↓
新请求取得同一个 Context

此时旧任务和新任务可能同时操作同一个 Browser Context，导致：

  • Page 被意外关闭。
  • 截图内容互相干扰。
  • 浏览器状态串扰。
  • 随机出现 Target closed 等协议错误。

因此，超时后的 Context 不能直接复用。正确做法是关闭整个 Context，并在确认旧 Context 已退出后创建新 Context，补回资源池容量。

问题三：20ms 轮询造成无效开销

原资源池在没有空闲 Context 时，每个等待请求都会每隔 20ms 检查一次：

const check = () => {
    const context = fetchIdleContext();

    if (context) {
        resolve(context);
    } else {
        setTimeout(check, 20);
    }
};

这种实现简单，但在高并发下会产生大量无效定时器。例如有 100 个等待请求时，每秒可能执行约 5000 次资源检查。多个 waiter 还会周期性同时醒来，形成类似“惊群”的竞争。

更麻烦的是，浏览器断线后旧资源池不会再获得 Context，这些轮询任务可能永远继续执行。

解决方案：统一托管 Context 生命周期

改造后的核心思路是：调用方不再直接负责获取和归还 Context，而是通过统一入口执行任务。

withContext(async (context, checkActive) => {
    // 使用 context 执行任务
}, timeout);

统一入口负责：

  1. 从资源池取得 Context。
  2. 执行渲染任务。
  3. 判断任务是否超时。
  4. 正常结束时归还 Context。
  5. 超时时关闭并替换 Context。
  6. 浏览器已经重连时，禁止旧 Context 回到新资源池。

Page 则在业务代码中通过 try/finally 清理：

const runner = await context.createRunEnv(false);

try {
    return await render(runner.page);
} finally {
    await runner.close();
}

这样无论任务成功、失败还是提前返回，Page 都能得到释放。

从轮询改为 waiter 队列

资源池没有空闲 Context 时，现在会保存请求对应的 Promise resolver：

请求进入 waiter 队列
        ↓
Context 被归还
        ↓
直接交给队首 waiter

这种实现具有几个明显优势：

  • 没有资源时不反复唤醒事件循环。
  • Context 归还后可以立即交接。
  • 每个 Context 只唤醒一个等待者。
  • 天然按照 FIFO 顺序处理。
  • 浏览器断线时可以一次性释放全部 waiter。

这里不需要引入完整的事件系统，一个简单的 Promise resolver 队列已经足够完成资源交接。

修复问题，但不改变业务语义

资源池重构很容易顺手改变超时范围，因此需要明确区分“生命周期管理”和“业务超时”。本次改造保持了原有约定：

  • HTML render 不增加 40 秒总超时。
  • screenshot 仍保留原来的 40 秒执行超时。
  • screenshot 的计时从成功取得 Context 后开始，不包含资源池排队时间。
  • 普通业务异常在 Page 清理成功后继续复用 Context。
  • 只有超时或浏览器换代时才销毁并替换 Context。
  • 原有重试范围和监控指标口径保持不变。

也就是说，改造解决的是资源所有权和异常隔离问题，而不是借机重新定义接口行为。

自动化验证

针对新的生命周期逻辑，补充了不依赖真实 Chrome 的检查，覆盖以下场景：

  • 多次 render 后资源池容量保持稳定。
  • 正常、提前返回和异常路径都能关闭 Page。
  • 普通业务失败不会无条件重建 Context。
  • screenshot 超时后旧 Context 不再复用。
  • 超时任务后续恢复时不能继续截图或重试。
  • Context 关闭完成前不会提前创建替代资源。
  • 浏览器断线后 waiter 能够正常退出。
  • 旧浏览器的 Context 不会进入新资源池。
  • Page 或 Context 初始化失败时能够正确清理。
  • render 不会被意外增加总超时。
  • screenshot 的 40 秒从资源获取完成后开始。

最终收益

  • 资源池容量能够长期保持稳定。
  • Page 和 Context 的泄漏路径得到控制。
  • 超时任务与后续请求彻底隔离。
  • 高并发下减少无效定时器和事件循环压力。
  • 浏览器断线后的恢复流程更加可靠。
  • 生命周期逻辑集中，调用方不再重复管理资源。
  • 在改善稳定性的同时保持原有业务语义。

总结

浏览器资源池最重要的并不是“池里有多少资源”，而是明确每个资源在任意时刻归谁所有。

一个可靠的资源池至少需要保证三件事：

  1. 每次获取最终都有对应的归还或销毁。
  2. 超时返回不等于底层任务已经结束。
  3. 已经失效的资源不能重新进入池中。

当资源所有权被统一管理后，很多偶发的 Chrome 错误、请求卡死和内存增长问题，都会从根本上变得更容易控制。
