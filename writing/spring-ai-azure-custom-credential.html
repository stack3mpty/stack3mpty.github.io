为 Spring AI 补回 Azure OpenAI 自定义身份认证能力

2026-09-08

在生产环境中使用 Azure OpenAI 时，API Key 并不总是最合适的认证方式。越来越多的团队开始使用 Microsoft Entra ID 和 Managed Identity，尤其是 User Assigned Managed Identity，以避免在配置文件中保存长期密钥。

不过，Spring AI 2.0.1 在接入新版 OpenAI Java SDK 后出现了一次认证能力回退：框架可以自动创建 Azure 默认凭据，却无法使用业务方自定义的 TokenCredential。

本文介绍这个问题的根因，以及 Spring AI PR #6937 采用的修复方案。对应问题记录在 Issue #6935。

问题背景

Spring AI 访问 Azure OpenAI，也就是现在的 Microsoft Foundry 时，会在内部创建默认 Azure 凭据：

new DefaultAzureCredentialBuilder().build();

DefaultAzureCredential 会依次尝试环境变量、Managed Identity、Azure CLI 等认证方式。对本地开发和简单部署来说，这套默认行为通常够用。

但在真实生产环境中，经常需要定制 DefaultAzureCredentialBuilder。例如，明确指定 User Assigned Managed Identity：

TokenCredential tokenCredential = new DefaultAzureCredentialBuilder()
    .managedIdentityClientId(clientId)
    .build();

常见使用场景包括：

  • 一个 Azure 资源绑定多个 Managed Identity。
  • 同一个应用访问多个 Azure OpenAI 资源。
  • 不同模型使用不同的身份。
  • 需要精确控制 Azure Credential Chain。
  • 运行环境无法依赖默认身份探测规则。

问题在于，即使应用成功创建了自定义 TokenCredential，也无法直接把它交给 Spring AI。

两套 Credential 类型之间的断层

Azure SDK 创建的凭据类型是：

com.azure.core.credential.TokenCredential

而 Spring AI 当前使用的 OpenAI Java SDK 接收的是：

com.openai.credential.Credential

Spring AI 内部其实已经实现了两者之间的适配：

AzureInternalOpenAiHelper.getAzureCredential(TokenCredential)

该适配逻辑会：

  1. 使用 Azure Cognitive Services 的默认 scope。
  2. 从 TokenCredential 获取访问令牌。
  3. 将令牌包装成 OpenAI SDK 的 BearerTokenCredential。
  4. 缓存访问令牌。
  5. 在令牌即将过期时刷新。

遗憾的是，AzureInternalOpenAiHelper 和它的适配方法都是 package-private，应用程序无法调用它。

DefaultAzureCredentialBuilder
        ↓
自定义 TokenCredential
        ↓
内部适配器不可访问
        ✕
OpenAiChatOptions.credential(...)

修复方案：提供一个公共适配入口

PR 没有重新实现认证逻辑，而是增加了一个非常薄的公共门面：

package org.springframework.ai.openai.setup;

import com.azure.core.credential.TokenCredential;
import com.openai.credential.Credential;

import org.springframework.util.Assert;

public final class AzureOpenAiCredentials {

    private AzureOpenAiCredentials() {
    }

    public static Credential from(TokenCredential tokenCredential) {
        Assert.notNull(tokenCredential, "tokenCredential must not be null");
        return AzureInternalOpenAiHelper.getAzureCredential(tokenCredential);
    }
}

新的 AzureOpenAiCredentials.from(...) 负责将 Azure SDK 的 TokenCredential 转换成 OpenAI SDK 所需的 Credential。

DefaultAzureCredentialBuilder
        ↓
自定义 TokenCredential
        ↓
AzureOpenAiCredentials.from(...)
        ↓
OpenAI SDK Credential
        ↓
OpenAiChatOptions.credential(...)

使用 User Assigned Managed Identity

首先添加 Azure Identity 依赖：

<dependency>
    <groupId>com.azure</groupId>
    <artifactId>azure-identity</artifactId>
</dependency>

然后创建自定义 Azure Credential：

import com.azure.core.credential.TokenCredential;
import com.azure.identity.DefaultAzureCredentialBuilder;

TokenCredential tokenCredential = new DefaultAzureCredentialBuilder()
    .managedIdentityClientId(clientId)
    .build();

通过新增的适配器交给 Spring AI：

import org.springframework.ai.openai.OpenAiChatOptions;
import org.springframework.ai.openai.setup.AzureOpenAiCredentials;

OpenAiChatOptions options = OpenAiChatOptions.builder()
    .credential(AzureOpenAiCredentials.from(tokenCredential))
    .build();

这样，Managed Identity 的选择权重新回到了业务应用手中。

为什么不直接修改 OpenAiChatOptions

另一种方案是让 OpenAiChatOptions 直接接收 Azure 的 TokenCredential，例如增加一个重载：

credential(TokenCredential credential)

但这会让 Spring AI 的通用 OpenAI 配置 API 直接暴露 Azure SDK 类型，从而带来几个问题：

  • 非 Azure 用户也会看到 Azure 专属 API。
  • 通用配置类型会与可选的 Azure 依赖产生耦合。
  • Credential 与 TokenCredential 重载可能增加 API 歧义。
  • Azure 认证细节会扩散到更多模块。

独立的 AzureOpenAiCredentials 更符合职责边界：

  • Azure 类型集中在 Azure 适配入口。
  • OpenAiChatOptions 继续使用 OpenAI SDK 的统一凭据类型。
  • 不改变现有默认认证行为。
  • 不影响使用 API Key 或非 Azure 服务的应用。
  • 未来可以在该类中扩展其他 Azure Credential 适配能力。

这是一次有意保持较小修改面的修复。

Token 缓存与刷新行为

公共适配器复用了现有的 AzureInternalOpenAiHelper，因此没有改变底层 token 管理行为。内部会为 Azure 请求固定的 Cognitive Services scope：

https://cognitiveservices.azure.com/.default

生成的 BearerTokenCredential 不会在创建时立即请求 token，而是在真正发送请求时才获取。

获取到的 AccessToken 会被缓存，后续调用复用缓存值，直到 token 接近过期。当前实现会预留五分钟刷新窗口，避免将马上过期的 token 交给 OpenAI 客户端。

这避免了每个模型请求都访问 Entra ID，同时也降低了请求过程中发生 token 过期的概率。

测试策略

PR 增加了针对公共入口的回归测试：

@Test
void publicFactoryAdaptsTokenCredential() {
    givenTokens(new AccessToken(
        "test-token",
        OffsetDateTime.now().plusHours(1)));

    Credential azureCredential =
        AzureOpenAiCredentials.from(this.credential);

    assertThat(azureCredential)
        .isInstanceOf(BearerTokenCredential.class);

    assertThat(((BearerTokenCredential) azureCredential).token())
        .isEqualTo("test-token");
}

结合原有测试，当前覆盖了：

  • 公共适配入口可以正常使用。
  • 请求使用正确的 Cognitive Services scope。
  • 创建 Credential 时不会提前获取 token。
  • 多次调用会复用缓存。
  • token 临近过期时会自动刷新。
  • Azure token 能正确传递给 OpenAI SDK。

定向测试共 6 项，全部通过；受影响 OpenAI 模块的编译、打包和 Javadoc 生成也均已通过。

总结

这个问题并不是 Spring AI 缺少 Azure 身份认证能力，而是已有能力被封装在内部，导致业务应用无法传入自定义 Azure Credential。

PR #6937 通过新增 AzureOpenAiCredentials.from(tokenCredential)，补齐了这段缺失的公共 API。它没有改变默认认证方式，也没有复制已有的 token 获取和缓存逻辑，只是把内部适配能力以边界清晰的方式开放出来。

对于使用 User Assigned Managed Identity、多 Azure 资源或复杂身份隔离策略的应用，这个入口让 Spring AI 的 Azure OpenAI 集成能够真正满足生产环境的认证需求。

参考：Spring AI PR #6937、Issue #6935，以及 OpenAI Docs 的 Azure OpenAI token provider 说明。
