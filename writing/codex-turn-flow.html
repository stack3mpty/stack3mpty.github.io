一次完整的Codex调用流程

2026-08-31

一次 Codex 调用从用户提交输入开始，经过 Session 控制循环、Turn 任务和模型工具循环，最终以 TurnComplete 事件结束。整条链路可以记成：

用户输入
  → Submission 队列
  → 决定 Start 或 Steer
  → RegularTask
  → run_turn
  → 模型与工具循环
  → TurnComplete 事件

1. 用户提交输入

上层从 CodexThread 发起调用：

thread.start_or_steer_turn(request).await

它最终会调用 SessionIo：

self.io.submit_turn_input(
    request,
    TurnInputMode::StartOrSteer,
).await

SessionIo 会生成 submission ID，创建一个 oneshot 回复通道，再把输入包装成 Submission：

Submission {
    id,
    op: Op::TurnInput {
        request,
        mode,
        reply,
    },
}

随后，Submission 通过 tx_sub 被发送给 Session：

CodexThread
    ↓ tx_sub
Submission Queue
    ↓ rx_sub
submission_loop

2. submission_loop 接收命令

submission_loop 是整个 Session 的控制循环。它从 rx_sub 中逐个读取命令，并按操作类型分发：

while let Ok(submission) = rx_sub.recv().await {
    match submission.op {
        Op::TurnInput { ... } => ...
        Op::Interrupt => ...
        Op::Shutdown => ...
        ...
    }
}

收到 Op::TurnInput 后，控制循环调用 turn_input::handle(...)，由它决定这次输入应该 Start 还是 Steer。

3. 决定 Start 或 Steer

StartOrSteer 会先通过 session.steer_input(...).await，尝试把新输入注入当前活动 Turn。这里有三种结果：

  • 存在可 steer 的 Regular Turn：输入加入 InputQueue，返回 Steered。
  • 没有活动 Turn：创建 TurnContext 并启动 RegularTask，返回 Started。
  • 存在 Review、Compact 等不可 steer 的 Turn：返回 NotSubmitted。

如果结果是 Steered，系统不会创建新 Turn，新输入由正在运行的 RegularTask 消费。如果结果是 Started，则进入任务启动流程。

4. 启动 RegularTask

Core 创建 RegularTask，然后交给 Session：

session.spawn_task(
    turn_context,
    input,
    RegularTask::new(),
).await;

spawn_task() 最终进入 start_task()，主要完成这些工作：

  • 把当前 Turn 注册为 active_turn。
  • 创建 CancellationToken。
  • 记录 Turn 启动时间。
  • 触发扩展生命周期。
  • 创建 tracing span。
  • 使用 tokio::spawn 启动后台任务。

后台任务执行 RegularTask::run(...)。因此，start_or_steer_turn() 不会等待整个 Turn 完成，只会等待 Core 给出“已启动”或“已 steer”的处理结果。

5. RegularTask 驱动 Turn

RegularTask::run() 首先发出 EventMsg::TurnStarted，然后尝试取得已经预热的 ModelClientSession，最后调用 run_turn(...)。

它的外层循环可以简化为：

loop {
    let last_message = run_turn(...).await?;

    if terminal_error {
        return Ok(last_message);
    }

    if !has_pending_input {
        return Ok(last_message);
    }
}

这层循环用于处理 Turn 即将结束时新到达的 steer 输入。如果结束边界出现了新输入，任务会继续运行，而不是过早退出。

6. run_turn() 执行核心 Agent Loop

run_turn() 是核心 Agent Loop。它先读取用户输入和对话历史，构造 StepContext 与 Prompt，再调用 Responses API 并处理模型的流式输出。

读取用户输入和历史
    ↓
构造 StepContext
    ↓
构造发给模型的 Prompt
    ↓
调用 Responses API
    ↓
处理模型流式输出

模型给出最终回答

当模型输出 Assistant Message，不再请求工具，并且没有 pending input 时，run_turn() 就可以结束。

模型发起工具调用

当模型输出 Tool Call 时，ToolRouter 会找到对应工具，执行 shell、MCP、apply_patch 等操作，再把 Tool Result 写入对话历史，随后重新请求模型。

模型输出 Tool Call
    ↓
ToolRouter 找到对应工具
    ↓
执行工具
    ↓
把 Tool Result 写入对话历史
    ↓
再次请求模型

工具执行后必须再次请求模型，因为工具结果只是原始观察，例如退出码和标准输出。工具本身不知道应该如何回答用户，模型还需要根据结果决定：

  • 是否需要继续调用工具。
  • 是否需要修复错误。
  • 任务是否已经完成。
  • 最终应该如何组织回答。

所以，核心循环实际上是：

模型
  → 工具调用
  → 工具结果
  → 模型
  → 工具调用
  → 工具结果
  → 模型最终回答

7. run_turn() 返回

当模型不再要求 follow-up，并且 InputQueue 中没有 pending input 时，run_turn() 返回：

Ok(Some(last_agent_message))

RegularTask 会在结束前再检查一次是否出现了新输入。确认没有新输入后，它也返回 Ok(last_agent_message)。

8. 发出 TurnComplete

start_task() 创建的后台包装任务拿到 RegularTask::run() 的结果后，会统一完成收尾工作：

  • flush rollout。
  • 清理 Task 状态。
  • 调用任务结束处理。
  • 触发 Turn 扩展生命周期。
  • 构造并发送 EventMsg::TurnComplete。
EventMsg::TurnComplete(TurnCompleteEvent {
    turn_id,
    last_agent_message,
    error,
    ...
})

事件通过 Session 的 tx_event 发送出去，最终到达客户端：

Session
    ↓ tx_event
Event Queue
    ↓ rx_event
CodexThread::next_event()
    ↓
App Server listener
    ↓
客户端

关键点：最终的 TurnComplete 不是由 run_turn() 直接发送，而是由 Session 的任务生命周期管理代码在 RegularTask 结束后统一发出。

一句话总结：Codex 把一次调用拆成命令接收、Turn 调度、Agent Loop 和生命周期收尾四层；Submission channel 负责输入，RegularTask 负责执行，模型与工具循环负责完成任务，TurnComplete 负责把最终状态交还给客户端。
