Codex的SessionIO和Session的区别

2026-08-31

SessionIo 和 Session 分离，本质上是把外部通信端点和内部运行状态分开。

外部 CodexThread                    内部 Session
┌─────────────────┐              ┌─────────────────┐
│ SessionIo       │              │ Session         │
│ tx_sub ─────────┼─────────────→│ rx_sub / loop   │
│ rx_event ←──────┼──────────────│ tx_event        │
│ status receiver │              │ status sender   │
└─────────────────┘              └─────────────────┘

1. 两者的职责不同

SessionIo 只保存通信与生命周期端点：

tx_sub
rx_event
agent_status
session_loop_termination

Session 则保存真正的运行状态：

history
active_turn
input_queue
services
tx_event

可以把两者理解为客户端接口与服务端实现的关系：

SessionIo = Session 的客户端接口
Session   = Session 的服务端实现

外部的 CodexThread 不需要直接接触 Session 内部状态，只需要持有 SessionIo，通过 channel 提交命令、接收事件和观察状态。

2. 让 submission loop 能正常关闭

这是把 SessionIo 从 Session 中分离出来最重要的原因。

submission_loop 大致是一个持续接收命令的循环：

while let Ok(submission) = rx_sub.recv().await {
    // 处理命令
}

当所有外部 tx_sub 都被销毁后，recv() 返回错误，循环自然结束。

如果 Session 自己也持有 tx_sub，生命周期就会形成自我维持：

submission_loop 持有 Arc<Session>
Session 持有 tx_sub
tx_sub 永远不全部销毁
rx_sub 永远不关闭
submission_loop 永远不结束

即使外部的 CodexThread 已经被销毁，Session 内部仍保留着一个 sender，receiver 就无法感知所有发送方已经离开。

分离以后，生命周期可以沿着 channel 的关闭方向自然结束：

CodexThread / SessionIo 被销毁
    ↓
tx_sub 全部销毁
    ↓
rx_sub 关闭
    ↓
submission_loop 退出
    ↓
释放 Arc<Session>

这样不需要额外设计一套“强制关闭循环”的状态协议。对象所有权和 channel 的关闭语义本身，就能驱动后台任务退出。

3. 明确通信的读写方向

拆分后的接口也让数据流向变得非常清楚：

  • 外部只能通过 tx_sub 向 Session 提交命令。
  • Session 只能通过 tx_event 向外发送事件。
  • 外部通过 rx_event 接收事件。
  • 外部只能观察 agent_status，不能随意修改内部状态。

这条边界限制了状态的修改入口：外部只能发消息，真正的状态变更由 Session 的控制循环串行完成。它既减少了状态竞争，也让 Session 的内部实现可以独立演进。

一句话总结：SessionIo 是 Session 的外部通信端点；分离它主要是为了明确通信边界，并让 channel 关闭能够可靠地驱动 Session 后台循环退出。
