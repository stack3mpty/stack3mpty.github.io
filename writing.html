Codex的并发模型设计

2026-08-31

Codex 的并发模型可以概括为：Tokio 异步运行时 + 每个 Session 串行控制 + Turn 内异步并发。

多个 CodexThread 并发运行
        │
每个 CodexThread 对应一个 Session
        │
submission channel
        ▼
submission_loop 串行处理控制命令
        │
        ├── 启动 RegularTask
        ├── steer 当前 Turn
        ├── interrupt
        └── approval / tool response
                │
                ▼
          run_turn 异步循环
                │
        模型请求 → 工具执行 → 再次请求模型

分层的并发结构

Codex 没有让所有操作直接竞争同一份状态，而是把并发拆成了几个层次。

  • Thread 之间并发：不同的 CodexThread 和 Session 可以同时运行，彼此不需要等待。
  • Session 内命令串行：submission_loop 从 rx_sub 中逐个读取 Submission，避免 start、steer、cancel 等控制操作发生状态竞争。
  • 任务异步执行：RegularTask 通过 tokio::spawn 执行，不会阻塞 submission_loop。因此模型运行期间，Session 仍然能够接收 steer 或取消命令。
  • Turn 内工具并行：当模型一次返回多个允许并行的工具调用时，这些工具可以并发执行，从而缩短一次 Turn 的整体耗时。

共享状态与消息通道

跨异步任务共享的对象通过 Arc 持有，active_turn、输入队列等可变状态则由 Mutex 或 RwLock 保护。锁负责局部的数据安全，而 Session 的串行控制循环负责更高层的状态一致性。

Channel 将 Session 与外部调用方解耦：

  • tx_sub / rx_sub：外部向 Session 发送控制命令。
  • tx_event / rx_event：Session 向外部发送运行事件。
  • oneshot：等待某个命令的单次处理结果。

取消机制

取消操作通过 cancellation token 通知正在运行的异步任务停止。它不要求控制循环同步等待任务退出，因此 Session 可以继续处理后续消息，同时由任务在合适的检查点响应取消信号。

像 Actor，但不是纯 Actor

从结构上看，这套设计很接近 Actor 模型：

  • Session ≈ Actor
  • Submission channel ≈ Actor mailbox
  • submission_loop ≈ 消息处理循环
  • RegularTask ≈ Actor 启动的后台异步任务

但它不是纯 Actor：后台任务仍然会通过 Arc、锁和 channel 与 Session 协作，并且一个 Turn 内部还可以继续派生并发工具任务。

一句话总结：Codex 用串行的 Session 控制循环保证状态一致性，用异步 Task 和并行工具执行保证吞吐量。
